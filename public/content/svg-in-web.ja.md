# WebページでSVGを使用する5つの方法とベストプラクティス（思考停止で使うのはやめよう）

正直なところ、フロントエンドのエコシステムにこれだけ長くいると、巨大なコードベースでSVGの扱いが完全にカオスになっているのを見るのが一番恐ろしいです。多くの開発者はデザイナーからSVGファイルを受け取ると、反射的に標準のJPGやPNGと同じように扱い、何も考えずに`<img>`タグに放り込んで作業を終えてしまいます。

その結果はどうなるでしょう？2日後、プロダクトマネージャーがやってきて、「ねえ、これにマウスをホバーしたとき、アイコンを青色にできない？」と言います。その時、`<img>`タグの中に詰め込まれたSVGは完全に死んでいることに気づくのです。CSSの`:hover`ステートはシャドウ境界を突き抜けてその`fill`（塗りつぶし）色を変更することは絶対にできません。そのため、わざわざデザイナーに頼んでSVGの青色バージョンを*もう一つ*エクスポートしてもらい、最終的にプロジェクトは`icon-home-default.svg`と`icon-home-active.svg`で肥大化します。これはフロントエンドエンジニアリングの災難です。

SVG（スケーラブル・ベクター・グラフィックス）は根本的に従来の「画像」ではありません。XMLで記述されたDOMツリーなのです！「WebページでSVGを正しく使用する方法」という問題を永遠に解決するために、今日は最も一般的な5つの方法をきっぱりと分解して解説します。堅苦しいトーンは抜きにして、実際のプロジェクトにおける本当のペインポイントとベストプラクティスについて語り合いましょう。

---

## 1. インラインSVG：UIコンポーネントの究極の王様

「インライン化」とは、テキストエディタでSVGファイルを開き、`<svg>...</svg>`コードの塊全体をコピーし、HTMLまたはJSXコードに完全にそのまま貼り付けることを意味します。

```html
<button class="nav-btn">
  <svg viewBox="0 0 24 24" class="icon-home">
    <path d="M3 9l9-7 9 7v11a2 2 0 0 1-2 2H5a2 2 0 0 1-2-2z"></path>
  </svg>
  ホーム
</button>
```

<strong>これは現在、最新のフロントエンドフレームワークで最も主流かつ強力な使用方法です。</strong>

なぜか？SVGがインラインDOMノードになると、CSSとJavaScriptがそれを自由に操作できるようになるからです。外部CSSに`.icon-home:hover path { fill: #3b82f6; }`と直接書くだけで、瞬時に色が変わります。JSを使ってあらゆる種類のクールなアニメーションをバインドでき、2つの別々の画像を読み込む必要は全くなくなります。最も重要なのは、追加のHTTPリクエストがゼロであるということです。

![コードビューから完全なインラインSVGコードを直接コピーする](/content/images/inline-svg-copy.png)

* (私たちはSVGエディター内に左右分割のSplit Viewモードを特別に構築しました。左側の「Copy SVG」をクリックすると、このワークフローのために特別に設計された、極限まで圧縮されたインラインコードを即座に取得できます。) *

<strong>致命的な欠点：</strong> SVGが信じられないほど複雑なイラスト（例えば数千行のコード）である場合、それを直接インライン化するとHTMLファイルのサイズが爆発的に増加し、初回レンダリングの解析速度が著しく低下します。さらに、インラインコードはブラウザによって独立してキャッシュされることはありません（HTMLに永久に結び付けられます）。

## 2. <img> タグ：イラストと思考停止の表示のための安全な避難所

これは誰もが最もよく知っている方法です：

```html
<img src="/assets/hero-illustration.svg" alt="美しいヒーローイラスト" />
```

**インタラクションが絶対に不要**で、**動的な色の変更も不要**な巨大なSVGイラストの場合、これは間違いなく最良の選択です。ブラウザはそれを標準の画像として扱うため、ブラウザレベルの独立したキャッシュメカニズムの恩恵を受け、遅延読み込みのために`loading="lazy"`を自由に使用できます。

<strong>最大の罠：</strong> 冒頭で述べたように、これは密閉されたブラックボックスとして機能します。コンポーネントの状態に基づいて頻繁に色を変更する必要があるUIアイコンには、絶対にこれを使用しないでください。

## 3. CSS Background：純粋な装飾要素の居場所

SVGが意味を持たない背景テクスチャや、ボタンの上の小さな装飾として使用されることがあります：

```css
.card-header {
  background-image: url('/assets/pattern.svg');
  background-repeat: repeat;
}
```

このアプローチは、プレゼンテーション（スタイル）と構造（HTML）を完璧に分離します。このアイコンがスクリーンリーダー（アクセシビリティ）にとって全く意味を持たない場合、それをCSSの中に埋め込むのが最もクリーンなアプローチです。

<strong>罠：</strong> 繰り返しになりますが、CSSで色を直接変更することはできません。しかし、高度な最新のテクニックとして、CSSの`mask-image`と`background-color`を組み合わせて色の切り替えを実現する方法がありますが、これには追加のCSSの工夫が必要であり、古いブラウザにはあまり優しくありません。

## 4. Data URI（Base64）：極小アイコンのためのパフォーマンスキラーか救世主か？

このようなスパゲッティのようなコードを見たことがあるはずです：

```css
.icon {
  background: url('data:image/svg+xml;base64,PHN2ZyB4bWxucz...');
}
```

SVGをBase64エンコーディングに変換し、CSSに直接詰め込みます。HTTP/1.1の時代には、フロントエンド開発者は接続リクエスト数を減らすためにこれを狂ったように使用していました。

<strong>私のアドバイスを聞いてください：時代は変わりました。</strong> 私たちは今、HTTP/2マルチプレキシングの時代にいます。数個のリクエストを節約するためだけにBase64をCSSに詰め込むのは、安物買いの銭失いです。Base64エンコーディングはファイルサイズを約33％肥大化させ、CSSファイルを巨大化させてページ全体のレンダリングをブロックします。

<strong>唯一の有効なユースケース：</strong> アイコンが極めて微小（1KB以下のローディングスピナーなど）であり、外部アセットパスに絶対に依存したくないUIコンポーネントライブラリの内部で使用される場合。控えめに使用してください。

## 5. SVG Sprite：エンタープライズアイコンライブラリの究極の答え

プロジェクトに100個のアイコンがあり、インラインSVGの柔軟な色変更が必要だが、100個の冗長なコードの塊でHTMLが肥大化するのは絶対に嫌だという場合、どうしますか？

答えは、`<use>`タグで構築されたSVGスプライトです。

メカニズムは簡単です。独立した`icons.svg`ファイルの`<defs>`タグ内にすべてのSVGパスを定義し、各パスに一意の`id`を与えます。

```html
<!-- ビジネスコードでは、このミニマリストな参照だけで済みます -->
<svg class="icon">
  <use href="/assets/icons.svg#icon-user"></use>
</svg>
```

![パフォーマンスを向上させるためにアイコンライブラリをSpriteに統合する](/content/images/icon-library-sprite.png)

* (システムに組み込まれたIcon Libraryのように。それらをSpriteに統合すれば、強力なブラウザキャッシュを享受しながら、プロジェクト内のどこでもいつでも呼び出すことができます。) *

ブラウザは`icons.svg`を一度だけロードすればよく、それをキャッシュします。後でページ上のどこでも`#id`を介して呼び出すたびに、HTMLコードを非常にクリーンに保ちながら、呼び出されたインスタンスの`fill`と`stroke`をCSS経由で変更することができます。最新のハイエンドコンポーネントライブラリ（エンタープライズUIキットなど）は、内部でほぼ全面的にこのアプローチを利用しており、多くの場合、自動ビルド生成のためのWebpack/Viteプラグインと組み合わせています。

## まとめ：では、実際に何を選ぶべきか？

哲学は飛ばして、結論に直行しましょう：

1. <strong>コアUIインタラクティブアイコン（ナビゲーションバー、ボタン）：</strong> <strong>インラインSVG</strong>または<strong>SVGスプライト（`<use>`）</strong>を強くお勧めします。色の変更は簡単で、リクエストのオーバーヘッドもありません。
2. <strong>記事のイラスト、巨大なヒーローバナー：</strong> 何も考えずに<strong>`<img>`タグ</strong>を選んでください。HTMLを引きずり下ろすことなく、キャッシュと遅延読み込みを享受できます。
3. <strong>背景テクスチャ、純粋な装飾：</strong> <strong>CSS Background</strong>に放り込んでください。DOM構造を純粋に保ちます。
4. <strong>Data URI：</strong> 独立してパッケージ化された極小コンポーネントを扱う場合を除き、可能な限り避けてください。

「グラフィックならimgタグを使う」という古臭い考え方は捨ててください。SVGをHTMLのインタラクティブな拡張として扱い始めましょう。それこそが、現代のフロントエンド開発者が持つべきベースラインのスキルなのです。
