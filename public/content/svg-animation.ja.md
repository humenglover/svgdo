# SVGアニメーションの血と汗と涙：初心者からキーボードを叩き割りそうになるまで

正直に言うと、この記事を書いている今、文字通りレガシーコードベースの別のSVGアニメーションのバグを修正している最中なんだ。その場で静かに回転するはずだったローディングサークルが、奇妙な遠心力でブラウザの左上隅を旋回し、画面外に完全に飛び去っていくのを画面で見つめているところだ。

今の俺の正確な気分は、下のGIFで完璧に表現されている。

![SVGアイコンが画面外に飛んでいくのを見ている俺の気分](/content/images/this-is-fine-css.gif)
*(これこそ文字通りフロントエンドエンジニアの日常だ。世界は燃えているのに、俺はまだCSSをいじっている)*

俺と同じような人がどれくらいいるかわからないけど、フロントエンドを学び始めたばかりの頃、CSSアニメーションなんていくつか`@keyframes`を貼り付けるだけだと思っていた。`transform: rotate(360deg)`の書き方を知らないやつなんているか？通常のHTMLの`div`や`span`をアニメーションさせるのは、目をつぶっていてもできる。しかし！特定の`<path>`や`<circle>`を個別にアニメーションさせようとするなど、SVG内のノードに触れた瞬間、絶対的な悪夢が始まるんだ。

今日、単純なアニメーションのためだけに半日もStackOverflowをあさらなければならないフラストレーションに、俺はもう完全にうんざりした。数年にわたってSVGアニメーションで遭遇したあらゆる落とし穴を手作業で吐き出すことに決めた。無駄話はなし、堅苦しい「第一に、第二に、最後に」といった構成もなしだ。痛みについてだけ話そう。

SVGアニメーションを作成するためにJavaScriptを使用してDOMを強引に操作しているなら、直ちにやめることを強く勧める。そんなゴミはメインスレッドを窒息死させるだけでなく、書いたコードは長く、悪臭を放つことになる。今は何年だ？スマホの画面でさえ120Hzのリフレッシュレートを持っている。俺たちにはGPUハードウェアアクセラレーションが必要であり、究極の滑らかさが必要なんだ。したがって、インラインSVGを純粋なCSSで駆動することが、現在絶対に唯一の真面目でラグのない解決策だ。

しかし、先ほど俺が不満を漏らしたように、SVGノードに回転アニメーションを追加した瞬間、それは100％コントロールを失って飛んでいく。なぜか？

俺たちが普段書いている通常のHTMLの世界では、要素の`transform-origin`（変形または回転する中心点）は、その正確な中心、つまり`50% 50%`にデフォルト設定されているからだ。
しかし、SVGの世界には信じられないほど奇妙な座標系がある！ほとんどのブラウザ（特にSafari、お前を名指ししているぞ）では、内部のSVGノードの変換の原点は、巨大なSVGキャンバスの左上隅`(0, 0)`に固定されるようにデフォルト設定されているんだ！

これはどれくらい愚かなことか？その場でくるりと回りたいのに、システムが3マイル離れた市庁舎広場を一周走るように強制するようなものだ！

俺はかつて、プロジェクトの立ち上げ前夜にこの問題を調査して午前3時まで起きていたことがある。結局、救世主は、多くのベテランでさえ聞いたことのないような、ばかげているほど無名なCSSプロパティであることがわかった。
回転する必要があるSVGノードのクラス名の下に、次の2行のコードを追加するだけでいい：

```css
.spin-gear {
  transform-origin: center center;
  /* 注目！これが神レベルの救済プロパティだ */
  transform-box: fill-box;
  animation: spin 2s linear infinite;
}
```

`transform-box: fill-box;`を追加すると、ブラウザはようやくバカではなくなる。ブラウザは理解する。「ああ、ボスはあの忌々しい巨大なキャンバスではなく、このグラフィック自体の実際のBounding Box（境界ボックス）をベースラインとして中心点を計算させたいんだな」と。
この1行のコードが、抜け落ちそうになっていたフロントエンドプログラマーの髪の毛をどれだけ救ったか神のみぞ知るだ。

回転以外にも、面接で自慢できるもう1つの派手なトリックが「線画アニメーション（Line Drawing Animation）」だ。
Appleの公式ウェブサイトや、極度に気取ったミニマリストのウェブサイトで絶対に見たことがあるだろう。マウスをスクロールすると、見えないペンでなぞっているかのように、画面上の曲線がゆっくりと描かれていくあれだ。

多くの人は、これは何かすごいCanvasライブラリやWebGLを使って書かれているに違いないと思っている。しかし実際には、純粋にCSSを使用するだけでSVGでこのアニメーションを無料で実現できる。
根本的な仕組みは、理不尽なほど巧妙だ。SVGの破線（ダッシュ）プロパティを利用している。

長さ1000ピクセルの線があると想像してみてくれ。
最初のステップとして、`stroke-dasharray: 1000;`を使用して、この線を「実線部分の長さが1000ピクセルで、空白のギャップも1000ピクセル」の巨大な破線に変換する。
2番目のステップで、`stroke-dashoffset: 1000;`を強引に使用して、この破線を左に1000ピクセルずらす。こうすることで、画面のビューポートに入ってくるのは、まさにその1000ピクセルの「空白のギャップ」になる。線は魔法のように消えてしまうんだ。
3番目のステップで、このオフセットを1000から0にゆっくりと戻すための非常に単純なCSSアニメーションを書く。

コードはこんな感じだ。信じられないほどシンプルだろ：

```css
.magic-line {
  stroke-dasharray: 1000;
  stroke-dashoffset: 1000;
  animation: draw-line 3s ease-in-out forwards;
}

@keyframes draw-line {
  to {
    stroke-dashoffset: 0;
  }
}
```
もともとビューポートの外側に隠れていた実線部分がゆっくりと引き戻され、視覚的にはその場に描画されているようにしか見えない。このトリックをマスターすれば、これからは社内のイケてるローディングアニメーションをすべて一人でこなせるようになる。

しかしそうは言っても、コードを書くのは単にコードを書くことだ。最初に受け取ったSVGがゴミで、座標系がめちゃくちゃで、意味のない`<g>`タグが7層も8層も入れ子になっていたら、CSSがどんなにすごかろうと役に立たない。アニメーションは間違いなくカクつき、遅延する。

だから、アニメーションを書くためにプロジェクトにSVGを放り込む前に、絶対にまずコードを洗わなければならない！

広告だらけのゴミみたいなオンライン圧縮サイトを使うのはやめろ。俺たち自身のSVGエディターを開いて見てくれ。完全にローカライズされたワークフロー全体を構築したんだ。下のGIFアニメーションを見てくれ。これは君のために特別に録画したもので、偽の視覚効果なしで純粋にローカルでレンダリングされている：

![エディターでゴミSVGを直接処理する](/content/images/icon-workflow-demo.webp)
*(これくらいスムーズなんだ。左側で操作し、右側で瞬時に純粋なコードを取得する。ネットワークの遅延に耐える必要は一切ない)*

デザイナーがお前に投げつけてきた、あらゆる汚く乱雑な座標を持つSVGを放り込め。Split View（分割ビュー）の下で、不要なメタデータを直接削除し、viewBoxをクリーンアップしろ。基盤となる構造がクリーンな場合にのみ、CSSで書いたインタラクティブなアニメーションは真に60FPSの滑らかさを実現できるんだ。

よし、愚痴はここまでだ、新しい要件が来た。プロダクトマネージャーが、ハートのアイコンをクリックしたときに跳ねるだけでなく、パーティクルのリングと一緒に爆発するようにする必要があると言ってきた。またSVGの座標系と戦いに行かなければならない。あの呪文を覚えておけ：`transform-box: fill-box;`。お前らが早く退勤できて、二度とエラーに遭遇しないことを祈っているぞ！
