# SVG 性能工程：如何在浏览器里流畅编辑 10 万节点的矢量图

先讲一个我们的编辑器差点被一张地图谋杀的下午。

有个用户拖进来一个 SVG 文件。表面上看毫无异常——750KB，一个 XML 文档，平时你发邮件都懒得压缩的那种大小。但我们的解析引擎一上手，数字就有点吓人：**3143 个 `<path>` 元素，9431 个 `d` 属性，9436 行标记语言。** 美国每一个县，各自是一个小多边形，每个多边形都是一颗等待诞生的 DOM 节点。

文件渲染出来了。然后用户抓住地图往画布上一拖。然后……这个标签页想起来自己是个网页，开始在码头上像条鱼一样大口喘气。不是崩溃——比崩溃更难受。是那种帧率低到你可以用手指头数帧的卡顿。光标已经把地图拖走了，地图三秒后才追上来，像一场和卫星通话的烂 Zoom 会议。

我盯着屏幕想：*这只是一个 750KB 的文件啊。一张猫打字的 GIF 都比它大。*浏览器凭什么溺水？

![荷马的头炸了](https://i.giphy.com/26gseQZ5oUvc2mkFi.gif)
*当我意识到一个 750KB 的文本文件里装着足以把浏览器拖垮的 DOM 节点时，我就是这个表情。*

那个答案——我花了很久、做了大量 profiling 才完全接受——是：**SVG 有一个肮脏的秘密：它不是图片格式，是 DOM 格式。** 每一个图形都是真实的、活着的 DOM 元素，要付 style、layout、paint 三笔账。而和所有 DOM 密集型技术一样，它有一道悬崖。这篇文章就是这道悬崖的工程尸检：为什么一个 750KB 的矢量文件能搞垮标签页，以及让 SVGDO 能流畅编辑 10 万节点矢量文件的全部招数——视口裁剪、LOD、AST diff、更新管线。

## 节点算术：每个 SVG 元素都是 DOM 公民

先从物理账开始，因为这是所有人都搞错的部分。

SVG 元素不是"一个图形"，它是一个 DOM 节点——MDN 说得很明确：SVG *生来就是为了和包括 CSS、DOM、JavaScript 在内的其他 Web 标准协同工作*（[来源](https://developer.mozilla.org/en-US/docs/Web/SVG)）。一个 `<path>` 是一个 `SVGPathElement`。它有样式、有 class、有事件监听器、有计算样式、在渲染树里有一席之地。它和 `<div>` 一样参与样式重算、布局、绘制——而且往往更贵，因为它的几何体是任意曲线，不是矩形。

所以当有人说"SVG 很轻量"时，他说的其实是**一个** SVG 很轻量。格式的缩放能力无可挑剔，**DOM 没有。** 来看这张规模阶梯，每一级都有真实参照物：

![SVG 节点成本](/content/images/articles/svg-dom-cost.svg)
*节点阶梯：图标 1 个节点、普通页面约 800 个（Lighthouse 警告线）、真实县地图 3143 个、10000+ 个触发 Lighthouse 报错、工业文件 10 万个。每上一级，style/layout/paint 的账单都翻着跟头涨。*

这些参照点值得好好引用。Google 的 Lighthouse "Avoid an excessive DOM size" 审计（[来源](https://developer.chrome.com/docs/lighthouse/performance/dom-size/)）：**页面的 body 超过约 800 个节点就警告，超过约 1400 个节点就报错**——注意这是对*整个网页*的阈值，还轮不到单独一张 SVG。审计文档自己列出了大 DOM 杀性能的三条路径：首屏不可见节点浪费网络字节、交互时不断重算节点位置与样式、脚本持有大量节点引用造成内存压力。

我们那张县地图有 3143 个节点——已经超过 Lighthouse 报错线 2.2 倍，而且它只是可编辑文档里的一层。再加一个图层、几个文字标签、一个水印图形、一层选框句柄……你的编辑器会话的 DOM 树，体量已经相当于一个小网站，只不过每个节点都是贝塞尔路径，每次交互都要重新布局。这就是问题的物理。浏览器不慢，是你让它养了一片森林，然后每帧都去戳它。

还有一件更反直觉的事：**SVG 规范对 `d` 属性没有长度上限**——MDN 的属性参考只规定语法，不设行数预算；浏览器也从未公开声明过"超过多少条指令我们就不管了"。这意味着复杂度的天花板不由规范决定，而由渲染引擎的耐心决定。你可以合法地写出一条几十万指令的 path，然后眼睁睁看着 paint 阶段从 16ms 涨到 1.6 秒——没有报错、没有警告，只是纯粹的慢。这种"合法但致命"的文档，恰恰是编辑器必须在它们进入 DOM 之前就驯服的对象。

## 为什么"只改一个东西"这么贵

这是杀死所有天真 SVG 编辑器的陷阱：**一次编辑的成本与编辑本身无关，与整棵树成正比。**

用户拖一个节点、改一个描边颜色、挪一个路径锚点，浏览器的管线就要重跑三个阶段：

1. **样式重算（Style recalc）**——遍历树、匹配选择器、重算计算样式。成本 = 节点数 × 选择器复杂度。
2. **布局（Layout）**——重算几何。在 SVG 里，几何变化会波及子节点（某些特性下还会波及*祖先*），所以根节点一变，底下全要重新布局。
3. **绘制（Paint）**——栅格化。对 `<path>` 来说，就是把贝塞尔曲线拍平、抗锯齿、填充区域。复杂路径在这一步很贵——一个 `d` 字符串里装着一万个指令的节点，就是一颗绘制成本吓人的"单节点"。

然后，把这三步在拖拽的每一帧里重复执行。天真的实现——"每次变化都更新 DOM，剩下的交给浏览器"——每个事件都跑完整条管线。3000 个节点时是卡顿，30000 个是幻灯片，100000 个时浏览器开始问你确定吗。

更气人的是：**大多数编辑根本不碰整棵树。** 你把一个图形从 (10,10) 拖到 (12,14)，只有这一个元素的坐标变了。另外 99999 个节点坐在那里，一模一样，等着被重新处理。天真编辑器为一颗叶子付整片森林的钱。

举个具体的例子：用户正在拖拽一条路径的锚点。天真的方案里，每一次 `pointermove` 都直接 `setAttribute('d', 新值)`，浏览器立刻重新解析、重新布局、重新绘制——如果一次拖拽产生 120 次 move 事件，就是 120 次全量管线。但在这 120 次里，只有最后一次的坐标有意义，其余 119 次中间值根本没人看得到。正确做法是把 120 次请求攒起来，一帧只提交一次——工作量不变，痛苦少了一百倍。

## AST 先行：别编辑 DOM，编辑模型

拯救一切的架构洞见是这一条：**编辑器的数据源，永远不该是 DOM。**

在 SVGDO 里，文件先被解析成 **AST**——一棵把所有元素、属性、路径指令都装进内存的对象树——所有编辑都发生在 AST 上。DOM 只是一层视图。用户改描边颜色，我们改的是 AST 里的一个节点，不是 DOM 元素。（这就是我们在《[别再把你的矢量节点传给野鸡服务器了](/resources/pictkit-architecture)》里讲过的纯前端架构：一次解析进内存，在内存里编辑，有节制地渲染。）

为什么这对性能如此重要？因为 **AST 的 diff 非常便宜**。对比两棵对象树，找出"这三个节点变了"，是微秒级的工作——不涉及样式重算、不涉及布局、不涉及绘制，DOM 甚至还没登场。贵的那部分只发生在把 diff *应用*到真实 DOM 的时候，而到那时你已经精确知道哪些节点变了。

对一个用户只编辑一个 path 的 10 万节点文件，AST diff 产出的补丁只有 **1 个元素**。这就是"重渲染一片森林"和"更新一片叶子"的区别。

## 视口裁剪：永远别为看不见的东西付钱

AST 解决了*更新*成本。但还有第二个更大的问题：*初始与稳态*成本。如果用户在一个 1200×800 的视口里看一张 50000×30000 单位的大文档，SVG 的绝大部分都在屏幕外——不可见，却仍然在每一帧消耗 style/layout/paint 的预算。

答案是图形学里最古老的招数：**视口裁剪——只渲染看得见的。**

![视口裁剪 + LOD](/content/images/articles/svg-viewport-culling.svg)
*一张 10 万节点文档，一个只显示其中约 2000 个节点的视口，以及一棵用 O(log n) 找出那 2000 个节点的四叉树。另外 98000 个节点，对渲染器来说根本不存在。*

实现栈，从浏览器原生到库：

- **`content-visibility: auto`**——一个告诉浏览器"视口外的子树跳过 style/layout/paint"的 CSS 属性。web.dev 关于 content-visibility 的文章（[来源](https://web.dev/articles/content-visibility)）实测渲染时间从 **232ms 降到 30ms——大约 7 倍提速**，用的就是一个包含大量屏幕外区块的页面。这是免费的原生裁剪，任何 SVG 重度页面都应该给屏幕外子树用它。
- **空间索引**——需要更精细的控制时（哪些元素在光标下、哪些在可视矩形里），四叉树是标准工具。d3-quadtree 模块（[来源](https://d3js.org/d3-quadtree)）的 `visit` API 就是干这个的："访问与某个矩形相交的所有节点"。在 10 万节点文档里找可视节点，从 O(n) 降到近 O(log n)。
- **渲染可视子集**——我们的渲染器遍历文档一次，用空间索引只收集与视口相交的节点，用这个子集构建 DOM。平移视口？重新查询、替换子树。DOM 永远只持有文档的可视切片。

数字一点不温和。如果你的视口只显示文档的 2%，裁剪让浏览器的稳态成本变成原来的 2%——*这还是在碰任何一个 path 之前*。

## LOD：让细节跟着缩放走

视口裁剪解决空间问题。LOD——*level of detail，细节层级*——解决*密度*问题：一个在 500% 缩放下占满屏幕的县多边形，在 5% 缩放下只有两个像素，毫无意义。

SVG 编辑的 LOD 阶梯：

- **缩得极小** → 渲染*简化*几何。合并小元素、合并子路径、减少每条路径的点数。
- **中等缩放** → 中等细节——保留主干结构，去掉噪声。
- **放大** → 完整保真——只有这时候才加载原始的、未简化的路径。

这就是 Google Maps 和所有游戏引擎用了几十年的细节金字塔逻辑，搬到 SVG 上严丝合缝，因为**路径简化是一个被解决得很好的问题**。经典算法是 Douglas-Peucker（也叫 Ramer-Douglas-Peucker，RDP）——一种 O(n log n) 的折线简化算法，贪心地丢掉那些偏离简化曲线小于容差的点。这是教科书级的计算几何，不是浏览器功能，所以把它当通用算法用；但对"这条 50000 点的路径变成 5000 点，在这个缩放下看起来一模一样"，它恰到好处。

日常的路径手术，`svgpath` 库（[github.com/fontello/svgpath](https://github.com/fontello/svgpath)）是我们的主力。它解析 `d` 属性字符串（不是 XML），给你一串链式 API，正好覆盖编辑器需要的变换——`round(precision)` 量化坐标并压缩字符串、`abs()/rel()` 在绝对/相对指令间转换（相对坐标压缩率更好）、`unarc()` 把弧线转成贝塞尔以便统一处理。再配上 `svgo`（[github.com/svg/svgo](https://github.com/svg/svgo)，22k+ star）剥离编辑器元数据、注释和次优默认值，"编辑前先优化"这一遍，通常能让文件体积和节点复杂度在 DOM 见到文档之前就双双缩水。

LOD 的回报：10% 缩放时，渲染器提供简化路径，节点数只有原来的零头；100% 缩放时提供完整几何——但只针对视口内的那几条路径。密度和面积，双双被驯服。

## 更新管线：diff、patch、批量、合成

到目前为止：编辑 AST、裁剪视口、按缩放简化。最后一根支柱是*变更如何上屏*——因为哪怕只有 3 个节点的补丁，用错了方式一样卡。

管线分五步：

1. **AST**——编辑修改内存模型。
2. **DIFF**——对比新旧 AST，产出最小变更集（"这个元素的这 3 个属性"）。
3. **PATCH**——用外科手术式的 `setAttribute` 调用把变更集应用到 DOM。不重建 `innerHTML`、不重新解析、不"替换整个 SVG"。
4. **批量（rAF）**——用 `requestAnimationFrame` 把自上一帧以来的所有变更合并成一次 DOM 更新。一次拖拽产生每秒 60 个事件；DOM 每帧只更新一次，而不是 60 次。
5. **合成（GPU）**——平移/缩放用 CSS `transform`，浏览器在 GPU 上合成，不重跑 layout 或 paint。

![更新管线](/content/images/articles/svg-update-pipeline.svg)
*AST → DIFF → PATCH → rAF → GPU。天真方案每个事件重渲染整棵树；管线每帧只更新变化的节点，且在合成器上完成。*

这些不是我们的观点——它们是浏览器官方的性能建议，来自 MDN 的 Canvas 优化教程（[来源](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)）：*"只渲染屏幕差异，而不是整个新状态"*、*"用 requestAnimationFrame 而不是 setInterval"*、*"CSS transform 更快，因为它使用 GPU"*。（那篇教程名义上是讲 `<canvas>` 的，但原则是通用的——它们讲的是浏览器的渲染管线，SVG 也共用同一条。）

还有一个值得点名的陷阱：**节流 vs 批量。** 用 `setTimeout(…, 200)` 做防抖会引入可感知的延迟，而且 DOM 更新仍在任意时刻触发。用 rAF 批量则恰好每帧触发一次，与显示同步——同样的工作量，零延迟。用帧预算，别用厨房定时器。

## SVG vs Canvas：什么时候承认失败

我来说句实话：这套方案是有边界的，不讲清楚边界的性能文章都是耍流氓。

如果你的场景是**每帧都在动的几万节点**——粒子系统、5 万节点的实时力导向图、实时可视化——SVG 就是选错了工具，到此为止。Canvas 就是为这个而生的：MDN 说它适合"动画、游戏图形、数据可视化、照片处理和实时视频处理"（[来源](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API)），它是一个*即时模式*位图表面：画、呈现、遗忘。没有 DOM 节点、没有样式重算、没有逐元素布局。对这种负载，canvas 或 WebGL 能把 SVG 按在地上摩擦，`OffscreenCanvas` 还能把它移到主线程外渲染。

但是——"canvas 更快"派总是跳过这部分——canvas 交出了让 SVG *可编辑*的一切：没有 DOM、没有无障碍（MDN 警告 canvas "内容不会像语义化 HTML 那样暴露给无障碍工具"）、没有对单个元素的 CSS 样式化、没有任意缩放下无限清晰。你没法在 DevTools 里检查 canvas 里的一个形状，没法给其中一个元素挂点击事件，没法让用户"编辑某一条路径"——全都只是缓冲里的像素。

对*编辑器*来说，诚实的工程答案是：**可编辑、可交互、语义化的那一层用 SVG；只有裸像素吞吐量占据主导时才用 canvas（或栅格化预览）。** 编辑器大部分时间只操作*一部分*元素，而不是同时操作全部——这恰好是 SVG 的 DOM 模型在裁剪、简化、diff 之后能轻松扛住的负载。10 万节点文件在 SVG 里能活；10 万节点的*粒子系统*活不了，也不该活。

而且就算你决定投降、全面改用 canvas，位图的天空也有限高：MDN 明确指出，大多数桌面浏览器允许 canvas 超过 10000×10000，但 iOS 设备把 canvas 限制在 4096×4096（[来源](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas)），超出后绘制命令静默失效。矢量文件"任意缩放都清晰"的承诺，在栅格化之后立刻作废——对编辑器来说，这是保留矢量层的又一个具体理由。

## 实战案例：被驯服的县地图

让我回到那张引发一切的县地图。这就是那个真实的文件——一张来自 Wikimedia Commons 的真实 750KB SVG，美国每个县都是独立的 `<path>`（[来源](https://commons.wikimedia.org/wiki/File:USA_Counties_with_FIPS_and_names.svg)）：

![美国县地图 SVG——3143 条路径](/content/images/articles/svg-counties-sample.svg)
*3143 条路径、9431 个 d 属性、9436 行、750KB。一个平平无奇的"小"矢量文件，却恰好是 Lighthouse DOM 报错线的 2.2 倍。*

在以上策略下，它会发生什么：

1. **一次解析**成 AST（750KB 在中端笔记本上约 15ms——XML 解析很快，从来不是瓶颈）。
2. **裁剪到视口。** 地图是 555×352 单位，编辑器视口只显示一片。渲染器只给可见切片物化 DOM——最多几百条路径，低缩放下其余部分用简化版本。
3. **按缩放走 LOD。** 缩小时，地图用简化路径渲染（RDP 到总共几百个点）；放大到堪萨斯州，渲染器为可见的县换上全保真几何——几条路径，完整细节。
4. **用 AST diff 编辑。** 用户改一个县的名称？一个 AST 节点变化，一次 DOM `setAttribute`，一次 rAF 批量。总成本：微秒。
5. **平移/缩放走 CSS transform**——GPU 合成，零重新布局。

天真路径上让标签页倒抽气的拖拽，现在稳稳锁在 60fps——因为浏览器的稳态 DOM 只有约 200 个节点而不是 3143 个，而手势只是 transform 的时候，每帧更新成本是*零*。

这一切不需要任何黑科技。它只需要拒绝让浏览器一次性看到整份文档。

## 结案陈词

县地图事件教会我的，和位图那一派人在栅格图像上学到的是同一个道理，只是翻译成了矢量：**浏览器不慢，是你的策略慢。** 一个 3143 条路径的 750KB 文件不是"大文件"——对解析器来说只是一次舍入误差。它只有在你把整份东西交给 DOM、还指望浏览器在每次交互时照看 3000 个活元素的那一刻，才会变成灾难。

四条铁律：

- **编辑模型，不编辑 DOM**——内存里的 AST，diff 后外科手术式打补丁。
- **看不见的就不渲染**——`content-visibility` + 空间索引做视口裁剪。
- **细节跟着缩放走**——用 RDP、svgpath、svgo 做路径简化，让密度和像素缩得一样快。
- **批量 + 合成**——rAF 合并、CSS transform 上 GPU，绝不为单个事件做全量重渲染。

矢量文件每年都在变大——户型图、城市地图、芯片版图、3D 打印切片预览、整份 CAD 导出。浏览器完全有能力编辑 10 万节点的文档。它只是需要你别再让它注意到这件事。

如果你正在开发自己的矢量编辑器，把这篇文章里的图存下来当检查单：先问 AST 在哪，再问视口外的节点还在不在 DOM 里，然后问一次拖拽触发了多少次全量重绘。三个问题都答对，你的编辑器就能扛住这个时代最疯狂的文件——那些从 CAD、GIS、芯片设计软件里导出的、动辄几十万节点的庞然大物。它们不是来刁难你的，它们只是长得比较大。
