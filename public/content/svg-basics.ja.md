# SVG入門：モザイクみたいなPNGを俺に送りつけるのはもうやめろ

正直なところ、後輩のデベロッパーを指導するたびに、俺が最も精神崩壊を起こす瞬間は、彼らがGitリポジトリを爆破したときではない。彼らがアセットをエクスポートするときに、絶対的な自信を持って、すべてのロゴ、小さなアイコン、さらには単純な曲線を持つ背景まで、すべてを透過PNGにスライスするときだ。

そして俺は、本来ならバターのようになめらかであるはずのモバイルページが、Retinaディスプレイではチェーンソーで切られたようにギザギザになっているのを無力に見つめることになる。アイコンのエッジがひどく荒削りだからだ。さらに致命的なのは、プロダクトマネージャーがやってきて「ああ、このアイコンの色はダークモードで変更する必要があるね」と言ったときだ。後輩は唖然とし、おずおずとデザイナーのところに戻って、色が調整されたPNGの新しいセットを懇願しなければならない。

これこそまさに、フロントエンド開発やUIデザインに携わっている限り、SVGとは一体何なのかを今すぐ、直ちに理解しなければならない理由なのだ。

## で、SVGって一体全体何なんだ？

「スケーラブル・ベクター・グラフィックス」の百科事典の定義なんか暗記しようとするな。あんなものは1990年代のコンピューターの教科書の戯言のように聞こえる。

最も直接的で、わかりやすい言葉で言うと：**SVGは「画像」ではない。それは数式とコードの塊だ！**

スマホで写真を撮って、JPGやPNGとして保存したと想像してみてくれ。この写真は、特定の色を持つ無数の小さな正方形のブロック（ピクセル）で構成されている。この写真を強制的に10倍に拡大しても、画面には依然としてその小さなブロックしか表示できない。そのため、画像はエッジがギザギザになり、ピクセル化されて、見るに堪えなくなる。これを「ビットマップ」と呼ぶ。

SVGはどうだろうか？SVGはピクセルを一切記録しない。
SVGファイルを開くと、全体が次のようなコードになっていることに気づくはずだ。

```xml
<svg viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" stroke="black" fill="red" />
</svg>
```

見えるか？これがSVGの真の姿だ。これは実際にはXML形式のコードの一部なんだ。
このコードはブラウザに次のように伝えている。「おい相棒、座標(50, 50)を中心にして、半径40の円を描いてくれ。ああ、そうだ、枠線は黒く塗って、中は赤で塗りつぶすのを忘れるなよ。」

数式だからこそ、奇跡が起こるんだ。**どんなに巨大で狂ったような高解像度ディスプレイに置いたとしても、それがAppleの最新のVision Proであっても、ブラウザは数式に基づいてリアルタイムで完全にゼロからそれを再描画するんだ！** だから、そのエッジは常に絶対的にカミソリのように鋭く、ぼやけることもなく、ギザギザになることも絶対にない！

## なぜお前のプロジェクトにはSVGが絶対に必要なのか？

お前は「俺は怠け者だから、PNGをスライスする方が簡単なんだ」と言うかもしれない。現代のワークフローでビットマップにしがみつくことが、なぜ基本的に死を求める行為なのか、今すぐ教えてやろう。

### 1. 恐ろしいほど小さいファイルサイズ

少し透過性のある標準的な3x高解像度PNGアイコンは、簡単に10KB、20KB、あるいはそれ以上に膨れ上がる。管理ダッシュボードに100個のサイドバーアイコンがある場合、アイコンをロードするだけで、ユーザーは空白の画面を何年にもわたって見つめることになる。
しかし、まったく同じアイコンをSVGで作成した場合、基本的には数行のテキストコードに過ぎない。GzipまたはBrotliで圧縮すると、ファイルサイズは通常わずか数百バイトになる！数百バイトとは一体どういう意味か？文字通り、単一のネットワークリクエストのほんの一部に過ぎない。帯域幅を節約するだけでなく、実際にWebページを瞬時にロードできるようになるんだ。

### 2. 神のように色を操る

冒頭で触れたダークモードの痛点を覚えているか？PNGを使用する場合、黒と白の2セットの画像を準備する必要がある。マウスのホバーエフェクトをサポートするためだけに、青のセットを準備しなければならないことすらある。
しかし、SVGを使用する場合、それはコードであるため、CSSを使用して直接制御できるんだ！

```css
/* すべてのアイコンが周囲のテキストの色を継承するようにする */
.my-icon {
  fill: currentColor;
}

/* ホバー時に攻撃的なホットピンクに変える */
.my-icon:hover {
  fill: #ff69b4;
  transform: scale(1.1);
}
```

この数行のCSSだけで、好きな色、好きなトランジションアニメーションを作ることができる。新しい画像をエクスポートするようにデザイナーに依頼する必要はまったくない。画像を1つずつ置き換えるよりも、この絶対的なコントロールの感覚の方が1万倍も良いと思わないか？

### 3. 恐ろしいインタラクティブの可能性

SVGは`<path>`や`<circle>`などのDOMノードで構成されているため、JavaScriptやCSSアニメーションを使用して、その中の1本の線や図形を具体的にターゲットにして操作できることを意味する。
たとえば、見えないペンで描かれたかのように線がゆっくりと自分自身を描画する、ハイエンドのWebサイトでよく見かけるあの超絶クールな「線画アニメーション（Line Drawing Animation）」。あれはSVGにしかできない。PNG？PNGはただの死んだピクセルの塊だ。不透明度を変更する以外は、何もできない。

## まだ有頂天になるな。SVGには落とし穴がある

SVGはUIアイコンのシナリオではすべてを完全に打ち砕くが、思い出してほしい。SVGは写真を保存するためのものではない。デザイナーが数百万のピクセルグラデーションと照明効果を含む非常に複雑な3Dレンダリングをお前に投げてきた場合、何があってもSVGへのエクスポートを強制してはならない。
なぜなら、ソフトウェアは数百万の小さなポリゴンコードを使用してその画像をシミュレートしようとし、最終的に数十メガバイトのサイズの怪物のようなXMLファイルを生成するからだ。ブラウザのCPUは、それをレンダリングしようとしたときに最大に達し、その場で死んでしまう。

さらに、デザインソフトウェア（FigmaやIllustratorなど）から直接エクスポートされたSVGには、ソフトウェア独自のゴミのようなメタデータ、無用なグループ（`<g>`タグ）、めちゃくちゃな座標系が詰め込まれていることがよくある。この生ファイルをコードに直接突っ込むと、肥大化するだけでなく、後でアニメーションを書こうとしたときに壊滅的な災害をもたらす。

したがって、プロジェクトにSVGを放り込む前に、データを洗浄しなければならない。
これこそまさに、俺が毎日この内蔵エディターを狂ったように使っている理由だ。純粋にローカルで実行されるため、ソースコードの漏洩を心配する必要はない。汚くて乱雑なコードを投げ込んで、最適化ボタンを押すか、手動でviewBoxを微調整するだけだ。出てくるのは、完全にクリーンで超高パフォーマンスの純粋なコードだ。

![当社のエディターを使用して、純粋にローカルでSVGのゴミコードを洗い流す](/content/images/icon-workflow-demo.webp)
*(左側にゴミコードを貼り付けると、右側で瞬時にクリーンな構造が得られる。強迫性障害のデベロッパーにとっての究極の福音だ)*

結論として、フロントエンドUIアイコンや単純なイラストにまだPNGを使用しているなら、お前は本当に自己反省する必要がある。SVGとコードベースのグラフィックを受け入れることが、現代のWeb開発における唯一の正しい姿勢だ。プロジェクトにある、地獄のようにぼやけたビットマップをすべて今すぐ交換しろ！
