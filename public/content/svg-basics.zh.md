## 所以，什么是特么的 SVG？

别去背百科全书上那种“可缩放矢量图形（Scalable Vector Graphics）”的狗屁定义，那玩意儿听起来就像是上世纪 90 年代计算机课本上的废话。

用最直接的白话来说：**SVG 不是一张“图片”，它是一堆数学公式和代码！**

想象一下，你用手机拍了一张照片，存成了 JPG 或者 PNG。这张照片是由无数个微小的、有着特定颜色的正方形小方块（也就是像素点）拼起来的。当你把这张照片强行放大 10 倍，你的屏幕依然只能显示那些小方块，于是画面就变得惨不忍睹，全是锯齿和马赛克。这叫“位图”。

而 SVG 呢？它根本不记录像素。
当你打开一个 SVG 文件，你会发现里面全是类似这样的代码：

```xml
<svg viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" stroke="black" fill="red" />
</svg>
```

看到了吗？这就是 SVG 的真面目。它其实就是一段 XML 格式的代码。
这段代码告诉浏览器：“嘿，哥们，麻烦你以坐标 (50, 50) 为圆心，画一个半径是 40 的圆。哦对了，记得边框涂成黑色，里面填满红色。”

既然它是数学公式，那么奇迹就发生了：**无论你把它放在多大、多变态的高清屏幕上，哪怕是放进苹果最新的 Vision Pro 里，浏览器都是根据公式当场、实时把它重新画出来的！** 所以它的边缘永远是绝对锐利的，永远不可能发虚，永远不可能有锯齿！

## 为什么你的项目里绝对需要它？

你可能会说，我就是懒，我就是觉得切 PNG 方便。我这就告诉你，为什么在现代开发流里，死抱着位图不放就是一种作死行为。

### 1. 极其恐怖的体积优势

一个普通的 3x 高清 PNG 图标，稍微带点透明度，体积轻轻松松干到 10KB、20KB 甚至更大。如果你一个后台系统有 100 个侧边栏图标，你光是加载图标就能让用户的首屏白屏半天。
而同样的一个图标，如果用 SVG，它本质上就是几行文本代码。用 Gzip 或者 Brotli 一压缩，体积通常只有几百个字节！几百个字节是什么概念？相当于一个网络请求的零头。它不仅省流量，还能让你的网页真正做到秒开。

### 2. 像上帝一样操控颜色

还记得我一开始说的深色模式的痛点吗？如果你用 PNG，你需要准备黑色、白色两套图，甚至为了支持鼠标悬停效果，还得再准备一套蓝色。
但如果你用的是 SVG，因为它是代码，你完全可以直接用 CSS 来控制它！

```css
/* 让所有的图标跟随外层文字的颜色 */
.my-icon {
  fill: currentColor;
}

/* 鼠标悬浮时变成骚气的猛男粉 */
.my-icon:hover {
  fill: #ff69b4;
  transform: scale(1.1);
}
```

就这几行 CSS，你想要什么颜色就有什么颜色，想要什么过渡动画就有什么过渡动画。根本不需要找设计师重新切图。这种掌控一切的感觉，不比你一张张去替换图片爽一万倍？

### 3. 可怕的交互潜力

既然 SVG 是由一个个 `<path>`、`<circle>` 这样的 DOM 节点组成的，那就意味着你可以用 JavaScript 或者 CSS 动画，单独针对这里面的某一条线、某一个形状进行操控。
比如那种高级网站上常见的、线条像被隐形的笔缓缓画出来的牛逼动画（Line Drawing Animation），只有 SVG 能做到。PNG？PNG 就是一坨死掉的像素，除了改改透明度，你什么都做不了。

## 别急着高兴，SVG 也有坑

虽然 SVG 吊打了一切 UI 图标场景，但我得提醒你，它不是用来存照片的。如果你的设计师丢给你一张包含了几百万个像素渐变、光影极其复杂的 3D 渲染图，你千万别强行用 SVG 导出。
因为软件会试图用几百万个微小的多边形代码去模拟那张图，最后搞出一个十几兆的怪物 XML 文件，你的浏览器在渲染时会直接把 CPU 吃满当场去世。

另外，从设计软件（比如 Figma 或 Illustrator）里直接导出的 SVG，里面通常塞满了设计软件自己用的垃圾元数据、没用的编组（`<g>` 标签）、以及乱七八糟的坐标系。如果你直接把这种原始文件塞进代码里，不仅体积臃肿，还会给后续写动画带来毁灭性的灾难。

所以，在把 SVG 丢进项目之前，你必须得洗一遍数据。
这也是为什么我每天都在疯狂使用我们自带的这个编辑器。它纯本地运行，不用担心源码泄露，直接把那些脏乱差的代码丢进去，一键优化，或者手动微调 viewBox，出来的就是绝对干净、性能极度炸裂的纯代码。
