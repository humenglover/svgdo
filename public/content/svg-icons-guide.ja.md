# アイコンデザインガイド：SVGから始まる完全なワークフロー（適当に線を引くのはやめよう）

正直なところ、これほど多くのレガシーなコードベースを引き継いできて、私が最も狂おしく感じるのは、`<img>`タグの乱用だけでなく、いかなる標準化も欠如したSVGアイコンの存在です。

プロジェクトのassetsフォルダを開くと、中のアイコンがカオスになっていることがあります。24x24のものもあれば200x200のものもあり、線幅が1pxのものもあれば1.5pxのものもあります。`fill`に`#333`がハードコードされているものもあれば、`<g>`グループの8つのレイヤーで包まれているものもあります。プロダクトマネージャーが「これらのアイコンにダークモードを追加して」と言うたびに、フロントエンドエンジニアはその場で辞表を提出したくなります。

SVGはデザインとコードの架け橋です。真に優れたアイコンセットは、「見た目が良い」というだけではありません。エンジニアリングレベルで厳密かつ制御可能でなければなりません。今日はおぼろげな美学のデザインについては話しません。最もハードコアな基礎となる仕様から直接始めて、エンタープライズグレードのSVGアイコンを実際にどのように描き、管理し、使用すべきかについて議論します。

---

## 1. アートボードを捨て、まずは「ピクセルグリッド」を構築する

Figmaで何気なくボックスをドラッグしてアイコンを描き始めるのが好きなデザイナーがどれほどいるかわかりません。これは絶対的なタブーです。

優れたUIアイコンは、絶対に厳密なピクセルグリッドに基づく必要があります。現在業界で最も普遍的な標準は、**24x24**のviewBoxです。針を描こうが象を描こうが、最終的に生成されるコードは次のようにならなければなりません。

```html
<svg viewBox="0 0 24 24" width="24" height="24">
```

### キーラインとパディング
24x24のアートボード内で、コンテンツを端まで絶対に詰め込まないでください！少なくとも2pxの安全なパディングを残す必要があるため、実際の描画領域はわずか20x20です。
なぜか？角丸長方形を円の隣に配置した場合、同じピクセル面積だと、視覚的に円の方が小さく見えるからです。この2pxの安全地帯を利用して、円をわずかに拡大し（20x20の制限を破り22x22に到達させ）、画面上で同じ大きさに見えるようにする必要があります。これを「光学的バランス（Optical Balance）」と呼びます。

![Split Viewの下でviewBoxとSVGソースコードをリアルタイムで確認する](/content/images/icon-split-view.png)

*当社のSVGエディターを使用する際は、コードの分割ビューモードに直接切り替え、最初の一瞥で`viewBox`が厳密に 0 0 24 24 であるかを確認する必要があります。そうでなければ、初期段階で作り直しのために突き返してください。*

## 2. ストロークの仕様：悪魔は細部に宿る

システムアイコンがリニアスタイルである場合、**ストローク幅は均一でなければなりません**。

24x24のアイコンの場合、**2pxのストローク**は、ほぼすべての大手ハイテク企業（Apple、Google、Microsoft）によって認められている黄金比です。非Retina画面では1pxは薄すぎに見え、1.5pxは一部の低解像度ディスプレイでサブピクセルレンダリングの問題（ぼやけ）を引き起こします。

```html
<path d="..." stroke-width="2" stroke-linecap="round" stroke-linejoin="round"/>
```

さらに、丸みを帯びた端点（`stroke-linecap="round"`）と丸みを帯びた結合（`stroke-linejoin="round"`）を使用することを強くお勧めします。これらは、低解像度でベクターグラフィックスに発生しやすいギザギザを大幅に相殺し、アイコンをはるかに滑らかで親しみやすく見せます。

最も重要なこと：**混在させてはいけません！** プロジェクトに1.5pxの検索アイコンと2pxのホームアイコンを同時に存在させることはできません。この視覚的な不連続性は、アプリケーション全体のプレミアム感を即座に低下させます。

## 3. カラーマネジメント：currentColorが唯一の真の神

ここはフロントエンド開発者とデザイナーの間の主要な紛争地帯です。デザイナーがエクスポートしたSVGには、多くの場合`#000000`や、さらに奇妙なカラー値が付随しています。

SVG内の色がハードコードされている場合、フロントエンド開発者がCSSを介してホバーステートやダークモードを制御するのは極めて苦痛になります（通常、無理やり色を変更するために見苦しいCSSフィルターを使用せざるを得ません）。

**唯一のベストプラクティス：メインカラーを`currentColor`に置き換えること。**

```html
<!-- 間違い -->
<svg fill="none" stroke="#333333">

<!-- 正解 -->
<svg fill="none" stroke="currentColor">
```

`currentColor`を使用することで、SVGはテキストのように機能し、親要素の`color`プロパティを自動的に継承します。外側のラッパーに`color: red;`と書けば、アイコンは赤くなります。ダークモードでテキストが白くなれば、アイコンも自動的に白くなります。クリーンでエレガント、そしてパフォーマンスのオーバーヘッドはゼロです。

## 4. スムーズな「WYSIWYG」ワークフローを徹底的に体験する

口で言うのは簡単です。技術的背景のないデザイナーにコードレベルの仕様に完全に準拠させるのは困難な場合が多々あります。これには、フロントエンド開発者がこれらのSVGを「クレンジング」して「プレビュー」するための非常に便利なワークフローを持つ必要があります。

私たちはSVGエディターに信じられないほど強力なワークフローを直接組み込みました。以下の純粋にローカルで録画されたリアルタイムのデモンストレーションアニメーションをご覧ください（これは外部へのリンクではありません。ローカル環境からスムーズに読み込まれています）。

![SVGアイコンのインポート、コードクレンジング、超高速エクスポートの完全なワークフローデモンストレーション](/content/images/icon-workflow-demo.webp)

アニメーションで示されているように、ライブラリから標準に準拠したアイコンをワンクリックで抽出したり、乱雑なソースファイルを投げ込んだりできます。左パネルのコントロールを使用して、**Split View**（分割ビュー）に直接切り替えます。視覚的なプレビューを見ながら、冗長な`<g>`タグ、無駄な`<defs>`、および色がハードコードされたゴミコードを容赦なく削除できます。確認したら、ワンクリックでExport（エクスポート）を押します。

IDEとブラウザの間を常にタブで行き来する必要はありません。これこそが、ベクターアセットを扱う際に現代のフロントエンド開発者が持つべき効率です。

## 結論：チェックリストを作成する

次回SVGアイコンのバッチを受け取ったときは、慌ててコードに投げ込まないでください。このチェックリストを実行してください：

1. **寸法の統一：** すべてのviewBoxは`0 0 24 24`ですか？
2. **一貫したストローク：** ストロークの幅は均一に`2px`（または設定した基準）ですか？
3. **色の継承：** すべてのハードコードされた色は`currentColor`に置き換えられていますか？
4. **コードの純度：** 冗長なタグやFigmaによって生成されたゴミコードは圧縮され、クリーンアップされていますか？

すべてに合格した場合、おめでとうございます。あなたのアプリケーションは細部の観点から、すでに質の悪いプロジェクトの80%を上回っています。標準は退屈かもしれませんが、エンジニアリングを持続可能に進化させるための唯一の基盤なのです。
