# ベクターノードを怪しいサーバーに漏らすのはやめよう：リアルタイムAST解析と純粋フロントエンドレンダリングのアーキテクチャ的優位性

数ヶ月前、同僚がSVGアイコンの編集ワークフローを見せてくれた。ストロークの色を変えるたびに、ファイルをオンラインエディタにアップロードし、サーバーが処理するのを待ち、変更を加え、そして結果をダウンロードする。たった一つの `stroke="#ff0000"` のためにだ。

数秒間、画面を無言で見つめた。それからPictkitを書き始めた。

これがデジタルプライバシーを守る崇高な使命として始まったなんて言うつもりはない。あのワークフローを見ていると身体的な苦痛を感じたから始めたんだ。しかし解析エンジンを構築していくうちに、問題は当初考えていたよりはるかに深いことがわかった。

---

## 第一部：残酷な現実

今日のWeb開発エコシステムでは、完全に狂気じみたことを当たり前にしてしまっている。すでにブラウザのRAM上にあるデータをテキストにシリアライズし、HTTPヘッダーで包み、何層ものネットワーク機器を通して数百キロも離れたサーバーに送信し、たった一つのXML属性を変更して、同じ経路で結果を返送する。

典型的な「オンラインSVGエディタ」で実際に何が起きているか、計算してみよう：

**ステップ1：シリアライズとパッケージング。** ブラウザはSVGコンテンツ（すでにメモリ上で文字列になっている）を `multipart/form-data` で包み込む。これは無料ではない。ブラウザはMIMEバウンダリを構築し、コンテンツをエンコードし、`Content-Length`を計算しなければならない。4KBのSVGに対して、このオーバーヘッドは2-3KB追加される。

**ステップ2：ネットワークの旅。** パケットはあなたのマシンを離れ、ローカルルーターを通り、ISPのモデムに到達し、いくつかのバックボーンホップを越え、最終的にデータセンターに到着する。光ファイバーの理想的な条件下でも、ネットワーク遅延だけで20-80msかかる。サーバーが別の地域や大陸にあれば、さらに100-300ms追加される。

**ステップ3：インフラストラクチャチェーン。** リクエストはロードバランサー（NGINX、HAProxy、またはAWS ALB）に当たり、アプリケーションサーバーに転送される。キューがあれば待たされる。それからサーバーは受信HTTPストリームを読み取り、`multipart/form-data`を解析し、ファイルを抽出して、ようやくSVGの処理を開始する。処理が終われば、またレスポンスをシリアライズする。

**ステップ4：誰も語らないセキュリティリスク。** 設定ミスのXMLパーサーはXXE（XML外部エンティティ）攻撃の侵入口だ。私は `resolveEntities: true` が有効になったパーサーを備えた「プロ向け」ツールを見たことがある。これにより攻撃者は次のようなコードを埋め込める：

```xml
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<svg>&xxe;</svg>
```

サーバーのパーサーがこのエンティティを解決すれば、`/etc/passwd` の内容がレスポンスに漏洩する。これは机上の空論ではない。2018年から2023年にかけて、画像操作サービスにおける安全でないXML処理に関連するCVEが200件以上報告されている。SVGをアップロードするすべてのオンラインツールが潜在的な攻撃ベクトルなのだ。

しかしセキュリティを無視しても、もっと根本的な問題がある：**すでに手元にある計算能力を無駄にしている。** モダンブラウザは驚くほど強力な仮想マシンだ。ChromeのV8エンジンはJavaScriptをネイティブマシンコードにコンパイルする。GPUはレンダリング作業を待っている。Web Workersを通じて複数のCPUコアにアクセスできる。IndexedDBでローカル永続化ができる。FileReader APIでファイルシステムから直接ファイルを読み取れる。

それなのに我々はそのパワーをどう使っているのか？文字列を見知らぬサーバーに送り、`element.setAttribute('fill', '#ff0000')` を実行してもらっている。フェラーリを持っているのに、近所のコンビニに行くのにUberを呼ぶようなものだ。

## 第二部：純粋フロントエンドの哲学

Pictkitは非常にシンプルで、ほとんど素朴とも言える前提から生まれた：**データがブラウザ上にあるなら、すべての処理はブラウザ上で行われるべきだ。** 以上。例外はない。「ユースケースによる」もない。

この哲学——私は「ゼロサーバーアーキテクチャ」または「物理的プライバシーアーキテクチャ」と呼んでいる——は三つの柱に支えられている：

### 柱1：プライバシー保証としての物理的分離

処理の100%がブラウザのサンドボックス内で行われるとき、プライバシーは利用規約の約束ではなく、物理法則となる。あなたのデザイン、企業アイコン、まだ発表されていない製品のモックアップ——すべてがあなたのマシンのRAMから出ることは決してない。DevToolsを開き、Networkタブに移動して、自分の目で確かめてほしい。外向きのリクエストはゼロだ。イーサネットケーブルを抜いても、Pictkitはまったく同じように動作し続ける。

これは「ポリシーによるプライバシー」ではない。「物理的不可能性によるプライバシー」だ。我々はたとえ望んでもデータを漏洩できない。コードにネットワーク送信のロジックが一切ないからだ。

### 柱2：GPUはあなたのもの——使い倒せ

すべてのモダンブラウザはGPUによるハードウェアアクセラレーションにアクセスできる。DOM内のSVG要素のスタイル属性を変更すると、ブラウザのレンダリングエンジン——ChromeではSkia、FirefoxではWebRender、SafariではCore Animation——が影響を受けるピクセルのみを再計算し、VRAMに送る。この処理は、60FPSを維持するためのフレームあたりの予算である16ミリ秒未満で完了する。

対照的に、サーバー・クライアント方式では：リクエスト送信 → 待機 → ビットマップ受信 → デコード → `<canvas>` に描画またはDOM置換。結果が届く頃には数秒が経過し、ユーザーの思考の流れは断ち切られている。

### 柱3：限界費用ゼロのコンピューティング

他人のサーバーで実行するすべての操作にはコストがかかる：CPU、メモリ、帯域幅、ストレージ。誰かがそれを支払い、最終的にそのコストはサブスクリプション料金、使用制限、さらに悪ければデータ販売の形でユーザーに届く。

Pictkitでは、あなたが実行するすべての操作の限界費用は我々にとってゼロだ。文字通りゼロ。あなた自身のCPUが処理し、あなた自身のGPUが描画し、あなた自身のハードドライブが結果を保存する。我々はただ一度だけコードを提供し、あとは道を空けるだけだ。これこそ真のスケーラビリティ——すべての新規ユーザーが自分のハードウェアを持ち込む。

## 第三部：技術的深掘り——実際の仕組み

よし、哲学は十分だ。コードを見ていこう。結局のところ、アーキテクチャは実装で証明されるのだから。

### 3.1 解析エンジン：XMLからASTへ1ミリ秒未満で

PictkitのエントリーポイントはFileReader APIだ。ユーザーがSVGファイルをブラウザにドラッグすると、`drop` イベントをインターセプトし、コンテンツを直接 `ArrayBuffer` に読み込む：

```javascript
const file = event.dataTransfer.files[0];
const reader = new FileReader();

reader.onload = (e) => {
  const rawBytes = new Uint8Array(e.target.result); // すでにRAM上
  const decoder = new TextDecoder('utf-8');
  const xmlString = decoder.decode(rawBytes);
  
  // マジックはここから：メインスレッドでの同期的解析
  const ast = parseSVGToAST(xmlString);
  
  // それからDOMに触れる
  renderASTToDOM(ast);
};

reader.readAsArrayBuffer(file);
```

重要な詳細に注目してほしい：`readAsText` ではなく `readAsArrayBuffer` を使っている。これにより文字デコードの完全な制御が可能になる。多くのSVGには `<?xml version="1.0" encoding="ISO-8859-1"?>` のようなエンコーディング宣言が含まれており、`readAsText` はそれを誤解釈する恐れがある。生のバイトを読み取ることで、解釈方法は我々が決める。

では `parseSVGToAST` は具体的に何をするのか？この関数はシステムの心臓部だ。XMLを一文字ずつ走査し、抽象構文木を構築する再帰下降パーサー（recursive descent parser）を実装している。構造解析に正規表現は使わない（壊滅的なバックトラッキングを引き起こす古典的ミスだ）。代わりに有限状態マシンを使う。

以下がレクサーコアの簡略版だ：

```javascript
function tokenize(xml) {
  const tokens = [];
  let pos = 0;
  
  while (pos < xml.length) {
    // 空白を消費
    if (/\s/.test(xml[pos])) {
      pos++;
      continue;
    }
    
    // 開始タグを検出
    if (xml[pos] === '<') {
      pos++;
      
      // コメント？ <!-- ... -->
      if (xml.slice(pos, pos + 3) === '!--') {
        const end = xml.indexOf('-->', pos);
        tokens.push({ type: 'COMMENT', value: xml.slice(pos + 3, end) });
        pos = end + 3;
        continue;
      }
      
      // 閉じタグ？ </g>
      if (xml[pos] === '/') {
        pos++;
        const nameEnd = xml.indexOf('>', pos);
        tokens.push({ type: 'CLOSE_TAG', name: xml.slice(pos, nameEnd) });
        pos = nameEnd + 1;
        continue;
      }
      
      // 開始タグ：<path d="..." fill="..." />
      const nameEnd = xml.indexOf('>', pos);
      const fullTag = xml.slice(pos, nameEnd);
      const spaceIdx = fullTag.indexOf(' ');
      const name = spaceIdx === -1 ? fullTag : fullTag.slice(0, spaceIdx);
      
      const selfClosing = xml[nameEnd - 1] === '/';
      const attrs = parseAttributes(fullTag.slice(name.length));
      
      tokens.push({
        type: selfClosing ? 'SELF_CLOSING_TAG' : 'OPEN_TAG',
        name,
        attributes: attrs
      });
      
      pos = nameEnd + 1;
      continue;
    }
    
    // タグ間のテキストコンテンツ
    const tagStart = xml.indexOf('<', pos);
    const text = xml.slice(pos, tagStart === -1 ? xml.length : tagStart);
    if (text.trim()) {
      tokens.push({ type: 'TEXT', value: text });
    }
    pos = tagStart === -1 ? xml.length : tagStart;
  }
  
  return tokens;
}
```

このレクサーは、現代のノートPCで典型的な5KB SVGを0.3ms未満で処理する。開発中に `performance.now()` で何十回も測定したから知っている。サーバーに邪魔されずにマイクロベンチマークを取れるのは、贅沢なことだ。

トークン化が完了すると、パーサーがASTを構築する。各ツリーノードは型付き属性、子ノード、元ファイル内の位置（後でソースコードにエラーをマッピングするため）などのメタデータを持つSVG要素を表現する：

```javascript
// 簡略化されたASTノード構造
{
  type: 'element',
  tagName: 'path',
  attributes: {
    d: { type: 'path_data', value: 'M 10 10 L 20 20 ...' },
    fill: { type: 'color', value: '#ff0000' },
    stroke: { type: 'color', value: '#000000' },
    'stroke-width': { type: 'number', value: 2, unit: 'px' }
  },
  children: [],
  sourceLocation: { line: 247, column: 4, length: 156 },
  computedBBox: null  // オンデマンド計算
}
```

なぜブラウザの `DOMParser` を使わずにASTなのか？良い質問だ。三つの理由がある：

1. **エラー制御。** `DOMParser` は不正なXMLに寛容すぎる。SVGにエラーがあると、`DOMParser` は黙って修復を試みるが、結果が予測不能なことがある。我々のパーサーはどの行・列に問題があるか正確に教える。

2. **元構造の保持。** `DOMParser` はXMLを正規化する：属性の順序を並べ替え、重要でないと判断した空白を削除し、エンティティを展開する。元のフォーマットを保ったままSVGを編集したい場合、これは災難だ。我々のASTはすべてのバイト情報を保持する。

3. **型付き属性。** DOMの属性は常に文字列だ。我々のASTでは、`stroke-width` は単位付き数値、`fill` は解析済み色（hex、rgb、hsl、名前付き色対応）、`d` は型付きパスコマンドのシーケンス。これにより意味的な検証と操作が可能になる。

![Pictkit AST Code Split](/content/images/articles/pictkit-ast-code-split.png)

### 3.2 プロパティパネル：外科的DOMミューテーション

ユーザーがSVG上のノードをクリックすると、エンジンはどのAST要素がそのポイントに対応するかを特定する。各要素のバウンディングボックスに対するヒットテストを行い、空間インデックス（viewBoxを象限に分割する単純なR-tree）で高速化する。

ノードが選択されると、Appearanceパネルに編集可能なプロパティが表示される。ここがPictkitの真価を発揮する場面だ：

```javascript
function updateNodeProperty(astNode, property, newValue) {
  // 1. プロパティタイプに対して新しい値を検証
  const validator = PROPERTY_VALIDATORS[property];
  if (validator && !validator(newValue)) {
    throw new Error(`${property} の無効な値: ${newValue}`);
  }
  
  // 2. ASTを更新（真実の源泉）
  astNode.attributes[property].value = newValue;
  
  // 3. 影響を受けるDOM要素のみを変更——他はそのまま
  const domElement = astNode._domRef;
  domElement.setAttribute(property, newValue);
  
  // 4. ブラウザが残りを処理：影響ピクセルのみGPU再描画
  
  // 5. Undo履歴にプッシュ
  undoManager.push({
    undo: () => updateNodeProperty(astNode, property, oldValue),
    redo: () => updateNodeProperty(astNode, property, newValue)
  });
}
```

ステップ3に注目：`domElement.setAttribute(property, newValue)`。ブラウザが再描画するにはこれだけで十分だ。DOM全体は再作成されず、ページレイアウトは無効化されず、グローバルなリフローもトリガーされない。レンダリングエンジンは特定の描画プロパティだけが変更されたことを検出し、局所的な再描画をスケジュールする。色だけの変更なら、GPUがピクセルバッファ内のいくつかの値を交換するだけで完了する。

その結果、不透明度のスライダーを0から1までドラッグしても、フレーム落ち一切なしでリアルタイムに変化を見られる。対照的にサーバー方式では：スライダー値をサーバーに送信 → 200ms待機 → 新しいビットマップ受信 → デコード → 表示。まったく異なる二つの体験だ。

![Pictkit Node Property Manipulation](/content/images/articles/pictkit-node-property-manipulation.png)

### 3.3 アフィン変換：ブラックマジックではなく、本物の数学

Pictkitを構築する中で最も啓発的な瞬間の一つが、変換の実装だった。「90°回転」をクリックすると、ほとんどのオンラインエディタはファイルをサーバーに送り、ImageMagickやlibrsvgで全座標を再計算させる。これは車のドアを開けるために外科医を呼ぶようなものだ。

実際には、2Dアフィン変換は3×3行列で表現される：

```
| a  c  e |
| b  d  f |
| 0  0  1 |
```

ここで：
- `a`、`d` はXおよびY方向のスケール
- `b`、`c` はスキュー（傾き）
- `e`、`f` はXおよびY方向の平行移動

`transform="matrix(1.04, 0, 0, 1.04, 0.02, 45.20)"` の意味はこうだ：104%の均一スケール、スキューなし、X方向に0.02px、Y方向に45.20pxの平行移動。

中心点 (cx, cy) を中心に点 (x, y) を角度 θ だけ回転させる：

```javascript
function rotatePoint(x, y, cx, cy, angleRad) {
  const cos = Math.cos(angleRad);
  const sin = Math.sin(angleRad);
  
  // 原点に移動、回転、元に戻す
  const dx = x - cx;
  const dy = y - cy;
  
  return {
    x: dx * cos - dy * sin + cx,
    y: dx * sin + dy * cos + cy
  };
}
```

しかしPictkitでは一点ずつ回転させたりはしない。数百の座標を持つパスには非効率だからだ。代わりに、新しい変換を要素の行列に合成する。要素がすでに変換 `T1` を持ち、回転 `R` を適用する場合、新しい変換は `R × T1`（3×3行列の乗算）：

```javascript
function composeMatrices(a, b) {
  // aとbはフラット配列として保存された3x3行列 [a,c,e, b,d,f, 0,0,1]
  return [
    a[0]*b[0] + a[1]*b[3] + a[2]*b[6],  // a
    a[0]*b[1] + a[1]*b[4] + a[2]*b[7],  // c  
    a[0]*b[2] + a[1]*b[5] + a[2]*b[8],  // e
    a[3]*b[0] + a[4]*b[3] + a[5]*b[6],  // b
    a[3]*b[1] + a[4]*b[4] + a[5]*b[7],  // d
    a[3]*b[2] + a[4]*b[5] + a[5]*b[8],  // f
    0, 0, 1
  ];
}
```

三行の浮動小数点演算。CPUはナノ秒で解決する。サーバーでは、SVG全体を送信し、処理キューで待ち、まったく同じ乗算を実行し（データセンターにいるからといって数学が変わるわけではない）、結果を返送する。この皮肉は格別だ。

**非アフィン変換については？** 自由変形や遠近変換などは？ここで大抵のエディタは白旗を上げてバックエンドに投げる。Pictkitでは、各パスのベジェ制御点に直接変換を適用し、`d` 属性を再構築する。CPU負荷は若干増えるが、数千ノードまでのSVGならまったく問題ない。

### 3.4 ラスターエクスポート：Canvas、GPU、そしてサーバーを使わない技

傑作をPNGやWebPにエクスポートする時が来た。従来のエディタなら：

1. SVGをサーバーに送信
2. サーバーがHeadless Chromeを起動（200-500MBのRAM）するかImageMagick/librsvgを呼び出す
3. ピクセルバッファにレンダリング
4. PNG/WebPにエンコード
5. 結果をストリーミング返送

Pictkitの方法：

```javascript
async function exportToPNG(svgElement, scale = 2) {
  // 1. SVGをData URIにシリアライズ
  const svgData = new XMLSerializer().serializeToString(svgElement);
  const svgBlob = new Blob([svgData], { type: 'image/svg+xml;charset=utf-8' });
  const url = URL.createObjectURL(svgBlob);
  
  // 2. Imageを作成してSVGを読み込む
  const img = new Image();
  await new Promise((resolve, reject) => {
    img.onload = resolve;
    img.onerror = reject;
    img.src = url;
  });
  
  // 3. 目標倍率でcanvasに描画
  const canvas = document.createElement('canvas');
  const bbox = svgElement.getBBox();
  canvas.width = bbox.width * scale;
  canvas.height = bbox.height * scale;
  
  const ctx = canvas.getContext('2d');
  ctx.scale(scale, scale);
  ctx.drawImage(img, 0, 0);
  
  // 4. GPUはすでにdrawImage()でラスタライズを完了している。
  //    あとはバイトを抽出するだけ：
  const blob = await new Promise(resolve => canvas.toBlob(resolve, 'image/png'));
  
  // 5. クリーンアップ
  URL.revokeObjectURL(url);
  
  return blob;
}
```

ここで起きている四つの重要なこと：

1. **`ctx.drawImage()` はGPUを使う。** SVGをcanvas 2Dコンテキストに描画するとき、ブラウザはCPUでラスタライズしない。Webページのレンダリングと同じハードウェアアクセラレーションパイプラインを使う。ChromeではSkiaとGPUを通る。結果：1000×1000 SVGの2倍スケールラスタライズが10ms未満。

2. **`canvas.toBlob()` が非同期なのには理由がある。** ブラウザは内部的にPNG圧縮を別スレッドに委譲でき、メインスレッドをUI応答のために解放する。

3. **サーバーサイドでJPEG品質設定を提供する必要なし。** `canvas.toBlob()` はMIMEタイプと品質をパラメータとして受け取る。シャープなエッジのグラフィックにはPNG、写真にはWebP、互換性にはJPEG。すべてローカル。

4. **最終ダウンロードは一行：** `<a>` 要素を作成し、`href = URL.createObjectURL(blob)`、`download = 'my-file.png'` を設定し、`click()` を発火し、URLを解放する。ブラウザがハードドライブに書き込むまで、ファイルはRAMから出ることはない。

![Mind Blown](/content/images/mind-blown.gif)
*最も近いサーバーにHTTPリクエストが届くよりも速く、ローカルGPUで2x/3x/4x解像度のベクターラスタライズができると気づいた瞬間。しかも誰にもあなたのデザインは見られない。*

## 第四部：実測値（マーケティングのフワフワした数字ではない）

具体的な数字で語ろう。実測。再現可能。

比較環境：M1 MacBook Pro、16GB RAM、Chrome 125、600Mbps対称光回線、AWS us-east-1サーバー（同一大陸、理想的条件）。テストSVG：4.7KBの「春巻き」アイコン、14個の `<path>` 要素、3層の `<g>` ネスト、線形グラデーション1つ。

### テスト1：ファイルオープン時間

| 指標 | 従来のクラウドエディタ | Pictkit |
|:---|:---|:---|
| TTFB（最初のバイトまで） | 0ms（ファイルはすでにローカル） | 0ms（ファイルはすでにローカル） |
| ネットワーク遅延 | 800ms - 2.5s（サーバー負荷に依存） | **0ms**（ネットワークなし、サーバーなし） |
| 解析時間 | バックエンド依存 + レスポンスシリアライズ | 0.3ms（自前パーサー）+ 2ms（DOMマウント） |
| **インタラクティブまでの合計** | **3-5秒** | **< 50ms** |

これは10%や50%の改善ではない。**60-100倍**の改善だ。ユーザー体験として言えば、「読み込み中にTwitterを見よう」と「まばたきする間もなかった」の差だ。

### テスト2：編集遅延（塗り色変更）

カラーピッカーでクリックを離してから画面上に最終結果が表示されるまでの時間。

| 工程 | クラウドエディタ | Pictkit |
|:---|:---|:---|
| ネットワークRTT | 80-150ms | 0ms |
| サーバー処理 | 50-200ms | 0ms |
| DOM更新 | レスポンス形式に依存 | **< 1ms**（`setAttribute`） |
| GPU再描画 | 8-16ms（データ受信後） | **< 16ms**（即時） |
| **体感合計** | **200-500ms** | **瞬間（< 16ms）** |

200-500msは大したことないように聞こえるかもしれないが、人間の脳がアクションを「瞬間」と感じる100msの閾値を超えている。Pictkitでの編集はネイティブアプリケーションと見分けがつかない。

### テスト3：2倍PNGエクスポート（出力約240KB）

| ステップ | クラウドエディタ | Pictkit |
|:---|:---|:---|
| SVGアップロード | すでにサーバー上 | 不要 |
| レンダリング | 1-3s（Headless Chromeまたはlibrsvg） | **8ms**（GPU経由canvas） |
| PNG圧縮 | 50-200ms | **15ms**（`canvas.toBlob`） |
| ダウンロード | 500ms - 2s（HTTPストリーミング） | **< 1ms**（ローカルblob URL作成） |
| **合計** | **2-5秒** | **< 30ms** |

## 第五部：このアーキテクチャの代償（無料の昼食はない）

トレードオフなしの完璧な解決策として提示するのは知的に不誠実だ。100%フロントエンドアーキテクチャには現実のコストがあり、それを文書化することが重要だと思う：

### 代償1：初期バンドルサイズ

完全なSVGパーサー、行列変換エンジン、Undo履歴マネージャー、ヒットテストシステム……積み重なれば大きくなる。我々のJavaScriptバンドルは処理を外部化するエディタより重い。パーサーはユーザーが実際にファイルを開いた時だけ読み込まれるよう、tree-shakingとコード分割に多大な努力を払ってきたが、それでも初期ダウンロードは大きい。

**我々の回答：** このコストを受け入れる。適切にキャッシュされた200-300KBのバンドルを一度ダウンロードする方が、サーバー呼び出しに依存する100KBよりも好ましい。二回目のインタラクションからは、すでに我々の勝ちだ。

### 代償2：ブラウザサンドボックスの制限

メインスレッドで50MBのSVGをUIフリーズなしに処理することはできない。非常に大きなファイルでは、解析をWeb Workerにオフロードし、レンダリングをチャンク分割する。しかし実用的な限界がある：約20MBを超えるファイルはブラウザで問題になり始める。

**我々の回答：** ユースケースの99.7%（アイコン、イラスト、Webグラフィック）では、SVGは1KBから2MBの間だ。地籍マップをSVGで編集する必要があるなら、おそらくタイルレンダリングを備えた専用ツールが必要だ。Pictkitはそれを目指さない。

### 代償3：クロスブラウザ一貫性

Firefox、Chrome、SafariでSVGレンダリングの実装に微妙な違いがある：フォントのアンチエイリアシング、色空間の扱い、`getBBox()` がときどき一貫しない値を返すこと。各ブラウザ向けの正規化レイヤーを書く必要があった。

**我々の回答：** Playwrightを使った自動ビジュアルリグレッションテストでブラウザ間のスクリーンショットを比較する。完璧ではないが、これらの差異をリモートサーバーでデバッグするよりはるかに保守しやすい。

## 第六部：結論——クラウドマーケティングを減らし、本物のエンジニアリングを増やせ

いいか、クライアント・サーバーアーキテクチャが特定の用途で理にかなっていることは理解している。ギガバイト級データセット、機械学習モデルのトレーニング、何百人もの同時ユーザー間の状態調整——これらには確かにサーバーが必要だ。すべての計算がローカルであるべきだと言っているわけではない。

しかし、SVGのような「ステロイドを打ったテキストファイル」を編集するのに？

**正当な技術的言い訳は一切存在しない。**

この業界は、「クラウド」という言葉が、いかに非効率であろうとアーキテクチャ上のあらゆる決定を正当化する魔法の言葉になってしまう不条理な地点に到達した。「クラウドで処理します」は現代的で、革新的で、スケーラブルに聞こえる。しかしそのマーケティングの裏には、居心地の悪い現実がある：ユーザーのデータを制御できないサーバーに送り、すべてのインタラクションに数百ミリ秒の遅延を追加し、その特権に対して金を払っているのだ。

Pictkitは別の道があることを示す私の試みだ。それは：

- **コードはデータのある場所で実行される。** その逆ではない。
- **プライバシーはシステムの物理的特性**であり、利用規約の条項ではない。
- **パフォーマンスはフレームで測られ**、サーバーレスポンスタイムではない。
- **スケーラビリティは無料**——すべてのユーザーが自分のハードウェアを持ち込む。
- **ユーザー体験はネイティブアプリと区別がつかない**——実質的にそうだからだ。

別に私のツールを使う必要はない。他にもフロントエンドファーストの選択肢はある。しかし、これからアーキテクチャを設計するたびに、自分に問いかけてほしい：**これはユーザーのブラウザで実行できるか？** 答えがイエスなら、そうしないための本当に、本当に良い理由が必要だ。

コードは正直だ。アーキテクチャもそうあるべきだ。
