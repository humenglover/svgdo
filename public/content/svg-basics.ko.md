# SVG 입문: 모자이크 같은 PNG 좀 그만 보내!

솔직히 말해서, 후배 개발자들을 가르칠 때 제가 가장 멘붕에 빠지는 순간은 그들이 Git 저장소를 날려버렸을 때가 아닙니다. 그들이 에셋을 내보낼 때 온갖 로고, 작은 아이콘, 심지어 단순한 곡선이 있는 배경까지 모든 것을 아주 당당하게 투명 PNG로 잘라낼 때입니다.

그러면 저는 원래 버터처럼 부드러워야 할 모바일 페이지가 Retina 화면에서 아이콘 가장자리가 전기톱으로 썰린 것처럼 너덜너덜해진 채로 나타나는 것을 무력하게 지켜볼 수밖에 없습니다. 더욱 치명적인 것은 제품 관리자가 다가와서 "아, 이 아이콘 색상을 다크 모드에서는 변경해야 해요"라고 말할 때입니다. 후배는 벙찐 얼굴로 디자이너에게 조심스럽게 다가가 색상이 조정된 새로운 PNG 세트를 달라고 애걸해야 합니다.

이것이 바로 당신이 프론트엔드 개발이나 UI 디자인을 하고 있는 한 당장, 즉시 SVG가 대체 무엇인지 이해해야만 하는 이유입니다.

![확대하면 PNG가 모자이크가 되는 이유를 후배에게 설명하려 할 때의 내 표정](/content/images/confused-math.gif)

## 그럼, SVG가 도대체 뭔데?

"스케일러블 벡터 그래픽스"라는 백과사전적인 정의 따위는 외우려 하지 마십시오. 그런 건 1990년대 컴퓨터 교과서에나 나오는 헛소리처럼 들립니다.

가장 직접적이고 쉬운 말로 하자면, **SVG는 "그림"이 아닙니다. 수학 공식과 코드의 덩어리입니다!**

휴대폰으로 사진을 찍고 JPG나 PNG로 저장했다고 상상해 보십시오. 이 사진은 특정 색상을 가진 무수히 많은 작은 정사각형 블록(픽셀)으로 이루어져 있습니다. 이 사진을 강제로 10배 확대하면 화면에는 여전히 그 작은 블록들만 표시될 수 있으므로, 이미지는 가장자리가 들쭉날쭉해지고 픽셀화되어 차마 눈뜨고 볼 수 없게 됩니다. 이것을 "비트맵"이라고 부릅니다.

SVG는 어떨까요? SVG는 픽셀을 전혀 기록하지 않습니다.
SVG 파일을 열어보면, 전체가 다음과 같은 코드로 되어 있다는 것을 알게 될 것입니다.

```xml
<svg viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" stroke="black" fill="red" />
</svg>
```

보이십니까? 이것이 SVG의 진정한 모습입니다. 실제로는 XML 형식의 코드 조각입니다.
이 코드는 브라우저에게 이렇게 말합니다. "이봐 친구, 좌표 (50, 50)을 중심으로 반지름이 40인 원을 그려줘. 아, 맞다, 테두리는 검은색으로 칠하고 안은 빨간색으로 채우는 거 잊지 말고."

수학 공식이기 때문에 기적이 일어납니다. **아무리 거대하고 정신 나간 고해상도 화면에 놓더라도, 심지어 Apple의 최신 Vision Pro라 할지라도 브라우저는 공식을 바탕으로 실시간으로 완전히 처음부터 다시 그려냅니다!** 따라서 그 가장자리는 항상 절대적으로 면도날처럼 날카롭습니다. 절대 흐려질 수 없고 톱니 모양의 가장자리가 생길 수도 없습니다!

## 당신의 프로젝트에 SVG가 절대적으로 필요한 이유는?

당신은 "난 그냥 게으르고 PNG 자르는 게 편해"라고 말할지도 모릅니다. 현대의 워크플로에서 비트맵에 매달리는 것이 왜 기본적으로 죽음을 자초하는 행위인지 지금 당장 말씀드리겠습니다.

### 1. 끔찍하게 작은 파일 크기

약간의 투명도가 있는 표준 3x 고해상도 PNG 아이콘은 가볍게 10KB, 20KB 또는 그 이상으로 부풀어 오릅니다. 관리자 대시보드에 100개의 사이드바 아이콘이 있다면, 아이콘을 로드하는 것만으로도 사용자는 한참 동안 빈 화면만 쳐다보게 될 것입니다.
하지만 똑같은 아이콘을 SVG로 만들면 본질적으로 몇 줄의 텍스트 코드에 불과합니다. Gzip이나 Brotli로 압축하면 파일 크기는 보통 몇백 바이트에 불과합니다! 몇백 바이트가 대체 무슨 의미일까요? 말 그대로 단일 네트워크 요청의 아주 작은 파편일 뿐입니다. 대역폭을 절약할 뿐만 아니라 실제로 웹페이지를 즉시 로드할 수 있게 해줍니다.

### 2. 신처럼 색상 조작하기

제가 처음에 언급했던 다크 모드에 대한 고충을 기억하십니까? PNG를 사용한다면 검은색과 흰색 두 가지 이미지 세트를 준비해야 합니다. 심지어 마우스 호버 효과를 지원하기 위해 파란색 세트를 준비해야 할 수도 있습니다.
하지만 SVG를 사용한다면, 그것은 코드이기 때문에 CSS를 사용하여 직접 제어할 수 있습니다!

```css
/* 모든 아이콘이 주변 텍스트의 색상을 상속받도록 함 */
.my-icon {
  fill: currentColor;
}

/* 마우스를 올리면 공격적인 핫핑크로 변신 */
.my-icon:hover {
  fill: #ff69b4;
  transform: scale(1.1);
}
```

이 몇 줄의 CSS만으로 원하는 색상, 원하는 전환 애니메이션을 마음대로 구현할 수 있습니다. 디자이너에게 새로운 이미지를 내보내 달라고 부탁할 필요가 전혀 없습니다. 이미지를 하나하나 교체하는 것보다 이 절대적인 통제감이 만 배는 더 좋지 않습니까?

### 3. 무서운 인터랙티브 잠재력

SVG는 `<path>` 및 `<circle>`과 같은 DOM 노드로 구성되어 있기 때문에 JavaScript 또는 CSS 애니메이션을 사용하여 그 안의 단일 선이나 도형을 구체적으로 타겟팅하고 조작할 수 있다는 것을 의미합니다.
예를 들어, 보이지 않는 펜이 그리는 것처럼 선이 천천히 스스로를 그려나가는 고급 웹사이트에서 자주 볼 수 있는 멋진 "선 그리기 애니메이션(Line Drawing Animation)" - 오직 SVG만이 그걸 할 수 있습니다. PNG요? PNG는 그냥 죽은 픽셀의 덩어리일 뿐입니다. 불투명도를 변경하는 것 외에는 아무것도 할 수 없습니다.

![직접 만든 SVG 애니메이션이 마침내 성공적으로 실행되는 것을 볼 때의 기분](/content/images/spongebob-rainbow.gif)
*(물론 그 애니메이션들을 조정하면서 좌표계 때문에 고문당해 죽을 뻔하는 것도 일상다반사입니다)*

## 아직 너무 흥분하지 마세요; SVG에도 함정이 있습니다

SVG가 UI 아이콘 시나리오에서는 모든 것을 완전히 압살하지만, 한 가지 기억해야 할 점이 있습니다. 사진을 저장하기 위한 것이 아닙니다. 디자이너가 수백만 개의 픽셀 그라데이션과 조명 효과가 포함된 매우 복잡한 3D 렌더링을 던져준다면, 무슨 일이 있어도 강제로 SVG로 내보내려 하지 마십시오.
소프트웨어는 수백만 개의 작은 다각형 코드를 사용하여 해당 이미지를 시뮬레이션하려고 시도할 것이고, 결국 수십 메가바이트 크기의 괴물 같은 XML 파일을 생성하게 됩니다. 브라우저의 CPU는 그것을 렌더링하려고 시도할 때 최대치를 찍고 그 자리에서 뻗어버릴 것입니다.

게다가 디자인 소프트웨어(Figma 또는 Illustrator 등)에서 직접 내보낸 SVG는 일반적으로 소프트웨어 자체의 쓰레기 같은 메타데이터, 쓸모없는 그룹(`<g>` 태그) 및 엉망진창인 좌표계로 가득 차 있습니다. 이 원시 파일을 코드에 직접 쑤셔 넣으면 용량이 부풀어 오를 뿐만 아니라 나중에 애니메이션을 작성하려고 할 때 재앙을 가져올 것입니다.

따라서 프로젝트에 SVG를 넣기 전에 반드시 데이터를 세탁해야 합니다.
이것이 바로 제가 매일 우리 내장 에디터를 미친 듯이 사용하는 이유입니다. 완전히 로컬에서 실행되므로 소스 코드 유출을 걱정할 필요가 없습니다. 그냥 더럽고 지저분한 코드를 던져 넣고 최적화를 누르거나 viewBox를 수동으로 조정하기만 하면 됩니다. 결과물은 절대적으로 깨끗하고 성능이 극도로 뛰어난 순수한 코드입니다.

![에디터를 사용하여 SVG의 쓰레기 코드를 순수 로컬에서 씻어내기](/content/images/icon-workflow-demo.webp)
*(왼쪽에 쓰레기 코드를 붙여넣으면 즉시 오른쪽에 깨끗한 구조가 나옵니다. 강박증 개발자들을 위한 궁극의 복음)*

결론적으로, 여전히 프론트엔드 UI 아이콘과 단순한 일러스트레이션에 PNG를 사용하고 있다면 정말 반성해야 합니다. SVG와 코드 기반 그래픽을 받아들이는 것만이 현대 웹 개발의 유일한 올바른 자세입니다. 서둘러 프로젝트에 있는 그 지옥같이 흐릿한 비트맵들을 모두 교체하십시오!
